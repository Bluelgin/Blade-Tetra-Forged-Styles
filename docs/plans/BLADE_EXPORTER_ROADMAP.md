# 名刀封存（Blade Exporter）——未来开发路线

> **状态：长期规划 / 概念设计，未进入实现。**
>
> 这份文件只保留未来开发方向、待验证的技术路线与验收目标；不代表当前版本已经提供导出器、创造物品、导出 JAR 或跨整合包兼容性。正式开始前，须重新基于当时的 main / 依赖版本调查。

## 1. 愿景

**让玩家亲手锻造的名刀，成为可从一个世界带去另一个世界的独立作品。**

BTFS 是创造工具，不应成为毕业后必须携带的依赖。玩家在 BTFS 世界中完成刀装、材料、名称、千门剑谱和能力搭配后，可以在有权限的创造模式下将其“封存”，生成一个可分享的拔刀剑附属 Mod。

**目标运行环境：** 先针对 Minecraft 1.20.1 / Forge 47.x / SlashBlade: Resharped 1.9.63～1.x 研究；导出的标准名刀目标环境**不要求安装 Tetra 或 BTFS**。它仍然需要对应版本的 SlashBlade。不同 Minecraft / 加载器版本需要单独移植与验证，不能将同一个 JAR 宣称为通用。

项目格言：**「名刀不必天生，亦可由你亲手锻成。」**

## 2. 设想的玩家体验（未实现）

1. 玩家正常游玩，使用 BTFS 和 Tetra 亲手锻造、命名和完善名刀。
2. 创造模式物品栏提供一个仅用于封装的工具，暂称 **「名刀封存」**。无生存合成途径；多人服务器操作还须验证权限，不能只信任客户端创造状态。
3. 玩家手持有效的 BTFS 模块刀使用该工具，打开导出界面；显示刀名、作者、简介、材料/刀装、当前剑谱、SA/SE、原始资源来源及兼容情况。
4. GUI 允许编辑独立 Mod 的名称、ID（安全校验）、版本、名刀 Tooltip / 传承文本、**3×3 合成表**、进阶前置要求（只开放目标端真实支持的条件）。
5. 转换器进行 **能力与许可检查**：可原样转换、需要轻量运行时、缺失依赖、不能合法打包、无法转换的部分必须分开列出，不允许悄悄宣称完全保留。
6. 玩家在确认预览后，安全地在本地导出 JAR（必要时先导出中间包，再交由离线打包器完成）。首次装入目标整合包后需重启游戏，让加载器注册 Mod。
7. 新整合包没有 Tetra / BTFS，仍能通过合成配方获取这把名刀，且可以使用**实际被成功转换**的外观、属性和能力。

保留玩家的作品署名、名刀故事和设计信息；不将真实用户名、存档路径等个人信息默认为公开内容。不得让生存模式或普通服务器玩家通过此工具任意写文件。

## 3. 导出边界与两种产物

### A. 标准名刀（优先）

**目标：仅依赖 SlashBlade（以及游戏/加载器正常前置），不依赖 Tetra / BTFS。**

转换内容：

- 名刀定义：名称、描述、静态攻击/耐久、附魔、原生剑型及可兼容的 SA / SE；
- 最终刀装/外观：从 Tetra 动态部件组合**烘焙**为目标拔刀剑可加载的独立模型、贴图及其他必要渲染资源；
- 合成表：从受控的 GUI 配方编辑器导出为目标版真实支持的 JSON 配方，需明确前置物品/模组依赖；
- 作者与作品信息：Tooltip、翻译和可选说明书、版权清单；
- 使用原生已有 ComboState 的刀：可用原生名刀数据的 `properties.root_combo` 指向**已注册**的连段入口。

**不承诺**仅凭名刀 JSON 即可生成任意连段、全新 SA/SE、原 BTFS 特有被动或特殊觉醒战斗。转换失败的能力须显式报错、可选择降级导出，不应静默替换。

产物可探索 Forge 的数据/资源型 Mod JAR（例如适配 `lowcodefml` 的方案），但打包形式仍需 PoC 验证，不能把“zip 改后缀”当成有效安装方案。

### B. 扩展名刀（后续）

**目标：支持千门剑谱与部分需额外逻辑的能力，仍尽量摆脱 Tetra / BTFS。**

- 先导出**已登记、已验证的普通动作序列**，利用 SlashBlade 原生 `ComboState` / `ComboStateRegistry` / 动作回调，而非另造攻击、动画、伤害引擎；
- 注册独立的连段入口（供 `root_combo` 引用），有界保存当前招式与中断条件、输入和超时控制；
- 轻量运行时可以选择由**导出附属携带编译后的最小实现**，或由独立于 BTFS/Tetra 的公共运行时提供。两者取舍以依赖数量、兼容和维护成本为准；
- 原 BTFS 动作、状态、秘传、VFX、觉醒、特殊 SA/SE 按“可直接复用 / 需要重新实现 / 暂不支持”逐项审计。不能因动作 ID 存在就认为已可导出；
- 不允许从用户输入、剑谱分享码或第三方资源自动执行任意 Java / 脚本 / 字节码，不导出不受信任的可执行逻辑。

在扩展层尚未通过真实联机验证时，UI 应仍能给出标准模式的明确降级预览。

## 4. 可复用的现有基础与证据（不是实现保证）

### BTFS 侧

- [千门剑谱玩家操作与验证](../guides/CUSTOM_STYLE_FINALIZATION.md)：可命名、排序、分享最多六招合法普通动作；动作推进依赖原生执行器及严格的服务端验证。
- [千门剑谱社区分享协议](../development/CUSTOM_STYLE_COMMUNITY_PROTOCOL.md)：分享码只是离线名称与动作顺序的数据表示，不是任意外部技能执行权限；不能未经校验直接用作导出输入。
- [名刀锭与模块化锻造](../guides/NAMED_BLADE_IMPRINTING.md)：刀身、鞘、镡等可动态引用名刀来源；**运行时引用不等于已完成静态模型导出**。
- [名刀附属兼容](../guides/ADDON_COMPATIBILITY.md)：部分第三方 OBJ 缺独立刀身/刀鞘/镡柄分组，需资源权限检查和安全回退。
- [当前觉醒刀架构](../awakened-rework/CURRENT_ARCHITECTURE.md)：四刀战斗和视觉具有多处 BTFS 状态/网络依赖；不得直接假设能进入基础导出。

### SlashBlade: Resharped 侧（1.20.1 Forge 源码调查起点）

- `SlashBladeDefinition` / `PropertiesDefinition` 数据定义有模型、贴图、属性、`slash_art`、`special_effects` 和 **`root_combo`**。
- `SlashBladeDefinition.getBlade()` 将根连段写入刀的状态；`ComboStateRegistry` 通过 Forge 注册 `ComboState`，动作节点负责下一招、超时、帧范围、click/tick/hit 等行为。
- **结论边界：** 名刀 JSON 能引用现存的根连段，不意味着仅以 JSON 声明就能动态注册新的 ComboState。扩展剑谱必须补上**独立的运行时注册与合法动作路由**。

源码入口（开始实现前应复核实际版本）：
- [PropertiesDefinition.java](https://github.com/mrqx0195/SlashBlade_Resharped/blob/master/src/main/java/mods/flammpfeil/slashblade/registry/slashblade/PropertiesDefinition.java)
- [SlashBladeDefinition.java](https://github.com/mrqx0195/SlashBlade_Resharped/blob/master/src/main/java/mods/flammpfeil/slashblade/registry/slashblade/SlashBladeDefinition.java)
- [ComboState.java](https://github.com/mrqx0195/SlashBlade_Resharped/blob/master/src/main/java/mods/flammpfeil/slashblade/registry/combo/ComboState.java)

## 5. 建议的阶段与验收门槛

| 阶段 | 范围 | 最小验收 |
| --- | --- | --- |
| 0. 技术 PoC | 在隔离样本里导出一把纯原生属性/材质/配方名刀；不引入 BTFS runtime | Forge 1.20.1 + SlashBlade 环境、不装 Tetra/BTFS，启动、制作、显示、攻击、保存再加载均正常 |
| 1. 静态封存 | 导出 BTFS 模块刀的静态模型、贴图、属性、说明与玩家定义的合成表 | 不复制未经许可的资源；检查持握、刀鞘、物品栏、刀挂台、资源重载；配方合法且能生存获取 |
| 2. 千门剑谱转换 | 做一把只有三个**原生合法动作**的自创连段名刀；使用独立注册的 `root_combo` | 左/右键、重连、超时、伤害、动画和服务端与客户端一致；不装 Tetra/BTFS 也能真实出招 |
| 3. 创造模式 GUI | 封存物品、作品元数据、合成表编辑、兼容/许可预览、受控的客户端导出 | 普通生存玩家及未授权多人用户不得导出；文件名和输出目录受控；失败无损坏产物 |
| 4. 扩展能力与分发 | 按需研究秘传/特殊 SA/SE/觉醒刀；元数据、版本约束、许可清单 | 每个能力单独验收，未支持项明确展示；无隐藏 Tetra/BTFS 依赖 |

阶段可拆分为独立小 PR，不绑定承诺日期。**第 0 阶段没有通过就不进入批量生成 JAR**，优先成熟技术和最小可运行原型。

## 6. 不可忽略的风险

- **安全与权限**：导出功能只由授权侧发起，严格区分客户端资源生成与服务器权威刀数据；不要从服务器文件系统随意读取/写出资源。路径、ID、JSON、压缩包内容都需验证和限额。
- **资源授权**：玩家从第三方 Mod 引用的 OBJ、纹理、音频、角色模型不自动拥有二次分发许可；输出需许可确认、署名与可复现的来源清单，无法授权的必须阻止打包或要求提供自己的素材。
- **动态效果丢失**：Tetra 材料系数、部件协同、动态贴图、特殊事件并不等价于 SlashBlade 静态值；需要转换报告和预览，不保证完全 1:1。
- **跨版本**：先锁定 1.20.1 Forge 的 SlashBlade 实装；1.21.1 NeoForge/Fabric 不是修改版本号就能运行。
- **网络与加载**：Mod 在启动时注册；游戏内生成 JAR 不意味着当前游戏可热加载它。联机双方通常需要匹配的运行时/资源文件。
- **持久化与重复导出**：输出的命名空间、内部 ID、资源路径需稳定，避免多个玩家的附属互相覆盖；同一输入尽量生成确定性文件；记录工具版本和目标依赖版本。
- **平衡**：不要把 BTFS 改装倍率和 SlashBlade 属性叠加计算；最终静态面板、伤害、SA/SE 需重新校对。
- **维护成本**：轻量运行时必须限制 API 面积；不建议把 BTFS 全量代码复制到每一个导出 JAR。

## 7. 明确非目标

- 本路线**不改变**现有 BTFS 生存玩法、千门剑谱或名刀锭的数据与配方。
- 不生成完全脱离 SlashBlade 的原版 Minecraft 武器。
- 不承诺自动兼容所有第三方名刀、模型、SA/SE 或自定义动画。
- 不默认提供上传服务器、在线市场、自动更新、用户作品云同步。
- 不在这份文档 PR 中开发 GUI、物品、JAR 生成器、战斗运行时，也不发布 Release。

## 8. 将来启动时的第一步

先完成一个**静态名刀的最小导出实验**，对应第 0 阶段：

1. 选择一把只使用原生属性、原生已有动作和获准使用资源的简单名刀；
2. 导出名刀定义、模型与贴图引用、翻译及一张简单的 3×3 合成配方；
3. 仅安装 Forge + SlashBlade，不装 Tetra/BTFS，验证启动、合成、物品栏与持握显示、普通攻击、保存与重新加载；
4. 出具明确的「已保留 / 需额外依赖或运行时 / 无法转换」报告，确认产物没有隐藏的 Tetra/BTFS 依赖。

**静态 PoC 判定：** 这把刀能在上述最小环境中正常获取、显示、使用和保存，才算第 0 阶段通过。该阶段可以使用原生默认连段，不要求先完成自创连段转换。

静态 PoC 通过后，再推进静态封存，并开展第 2 阶段的**独立三招转换实验**：

1. 从已有合法剑谱导出三招顺序与名称；
2. 为输出名刀注册自己的原生 ComboState 入口并复用被允许的动作回调；
3. 在名刀数据中填入 `root_combo`、外观与简易可获取的配方；
4. 仅安装 Forge + SlashBlade，分别单机/专服测试输入、同步、伤害、模型、存档；
5. 根据转换报告决定后续正式用户界面与生成流程。

**三招 PoC 判定：** 如果输出刀必须依赖 BTFS/Tetra 才能进行三招连段，或者只是使用默认动作而没有执行所导出的三招顺序，就不算第 2 阶段成功。
